Feedsss Project Guide

This document explains the Feedsss project end to end: what it does, which technologies it uses, how the frontend and backend are organized, how each service works, and what the current implementation gets right and still needs improvement.

Frontend: React + Vite Backend: Express + MongoDB Media: Cloudinary Auth: JWT + OTP Email Flow

1. What This Project Is

Feedsss is a social feed application with moderated posting. Regular users can register, verify their email, log in, create a post with an image, browse approved posts, like posts, and view their own profile. Admin users can review pending posts and decide whether to approve or reject them.

The app follows a common full-stack split:

  • frontend/ contains the user interface and client-side logic.
  • server/ contains the API, database models, auth logic, email flow, and upload handling.

2. High-Level Feature Set

User Features

  • Register with username, email, phone, password, and role.
  • Verify account using an email OTP.
  • Log in and persist session info in the browser.
  • Request a reset-password OTP and set a new password.
  • Create image posts with captions.
  • See approved posts in the main feed.
  • Like and unlike posts.
  • View a profile page with personal posts and approval status.

Admin Features

  • Open an admin dashboard.
  • Fetch posts that are still pending moderation.
  • Approve a post so it becomes visible in the public feed.
  • Reject and delete a post that should not go live.

5. Frontend Architecture

The frontend is a single-page React application. Routing is configured in App.jsx, where each URL path maps directly to a page component.

Frontend Pages

  • / Home landing page with login/register actions.
  • /login User login form.
  • /register Registration form.
  • /verify-otp OTP screen for account verification.
  • /forgot-password Request reset OTP.
  • /reset-password Verify reset OTP and change password.
  • /feed Main approved-post feed.
  • /profile User profile and post history.
  • /create-post Caption + image upload form.
  • /admin Moderation dashboard.

Frontend Service Layer

The UI does not call raw URLs everywhere. Instead, it uses a small service layer:

  • services/api.js creates a shared Axios instance.
  • services/authService.js wraps auth-related API calls.
  • services/postService.js wraps post-related API calls.

This keeps page components cleaner and makes API behavior more consistent.

Frontend State Handling

State is handled locally with React hooks like useState and useEffect. There is no global store such as Redux or Zustand. Current user data is read from and written to localStorage.

The app uses a simple local-state approach, which is easy to understand for smaller projects but can become harder to manage as auth rules, permissions, and cross-page state grow more complex.

6. Backend Architecture

The backend is an Express API server started from server.js. It loads environment variables, connects to MongoDB, enables middleware, and mounts two route groups:

  • /api/auth for registration, login, OTP, password reset, and logout.
  • /api/posts for creating, reading, moderating, liking, and deleting posts.

Backend Layers

  • routes/ defines endpoint URLs.
  • controllers/ contains request logic.
  • models/ defines Mongoose schemas.
  • config/ initializes MongoDB and Cloudinary.
  • middleware/ provides auth and upload utilities.

7. Database Models

User Model

  • username: display name.
  • email: unique identifier for login.
  • phone: stored as plain string.
  • password: hashed password string.
  • avatar: avatar URL with a default DiceBear fallback.
  • role: either admin or user.
  • isVerified: whether email verification is complete.
  • otp, otpPurpose, otpExpires: support OTP flows.

Post Model

  • content: caption text.
  • image: image URL returned from Cloudinary upload.
  • userId: MongoDB reference to the owning user.
  • username and avatar: copied onto the post for easy display.
  • likes: array of user IDs that liked the post.
  • approved: moderation status, defaulting to false.

8. Authentication and Authorization

Registration Flow

  1. User submits registration form.
  2. Backend checks if the email already exists.
  3. Password is hashed with bcrypt.
  4. A 6-digit OTP is generated.
  5. User is saved with isVerified = false.
  6. OTP is emailed to the user.
  7. Frontend redirects to the OTP verification screen.

Email Verification Flow

  1. User enters the OTP.
  2. Backend fetches the user by email.
  3. OTP and expiration time are checked.
  4. If valid, isVerified becomes true.
  5. OTP fields are cleared from the database.

Login Flow

  1. User submits email and password.
  2. Backend compares the password against the bcrypt hash.
  3. Backend refuses login if the account is still unverified.
  4. JWT is created with user ID and role.
  5. JWT is returned and also set as an HTTP-only cookie.
  6. Frontend saves user data and token in local storage.

Password Reset Flow

  1. User enters email on the forgot-password page.
  2. Backend generates and emails a reset OTP.
  3. User enters OTP and new password on the reset page.
  4. Backend verifies OTP.
  5. Backend hashes the new password and updates the account.
  6. OTP fields are cleared again.
There is an auth middleware file that can verify JWT cookies and restrict admin-only access, but it is not currently applied to the post routes. That means the backend is not really enforcing access control yet.

9. Post and Media Handling

Post Creation

Users create posts from the frontend with a caption and one image file. The browser builds a FormData request, and the backend uses Multer with a Cloudinary storage adapter to upload the image directly. After upload, the post is inserted into MongoDB with the hosted image URL.

A new post is not visible in the public feed immediately because its approved field starts as false.

Feed Retrieval

The public feed endpoint returns only posts where approved: true. Posts are sorted newest first and use Mongoose populate() for related user and likes data.

Likes

Likes are implemented as a toggle. If the user ID is already in the post's likes array, it is removed. Otherwise it is added. The server responds with the new count and whether the current user has liked the post.

10. Admin Moderation Flow

  1. Admin page fetches posts with approved: false.
  2. Admin can approve a post, which updates approved to true.
  3. Admin can reject a post, which deletes it from the database.
  4. Approved posts then appear in the public feed.
Moderation is a strong product idea here because it creates a cleaner feed and gives the project a more distinct workflow than a simple post-anything social app.

11. UI and Design System

The frontend uses a custom visual theme instead of default Tailwind-only utility styling. The design language includes:

  • Gradient backgrounds and glassmorphism-style cards.
  • Warm pink, orange, and violet accent colors.
  • Responsive top bars, cards, and mobile-friendly layouts.
  • Light motion and animated floating background orbs.
  • Reusable classes for buttons, inputs, post cards, and profile cards.

This gives the app a more polished look than a bare CRUD project and makes it easier to explain visually in a portfolio setting.

12. Service-by-Service Explanation

API Service

The shared Axios instance sets the API base URL from VITE_API_URL and enables withCredentials so cookies can travel with requests.

Auth Service

The auth service groups all authentication-related requests: register, verify OTP, login, forgot password, verify reset OTP, reset password, and logout.

Post Service

The post service groups post retrieval, creation, pending moderation, approval, rejection, liking, user-profile posts, and deletion.

Email Service Behavior

Email sending is handled directly inside the auth controller via a Nodemailer transporter configured for Gmail SMTP. Both registration and password reset reuse the same OTP generation approach.

Upload Service Behavior

Multer delegates file storage to Cloudinary, so uploaded files do not remain on the local server filesystem. Instead, Cloudinary hosts them and returns a URL used by the app.

13. Request Flow Examples

A. Register to Verified Account

User fills Register form
-> frontend authService.register()
-> POST /api/auth/register
-> authController.register()
-> User saved with hashed password and OTP
-> OTP email sent
-> frontend redirects to verify page
-> frontend authService.verifyOTP()
-> POST /api/auth/verify-otp
-> authController.verifyOTP()
-> user.isVerified = true

B. Create a Post

User fills caption and selects image
-> frontend builds FormData
-> postService.createPost()
-> POST /api/posts/create
-> multer upload middleware
-> Cloudinary upload
-> postController.createPost()
-> Post saved with approved = false
-> admin must approve before it appears in feed

C. Like a Post

User taps like
-> postService.likePost(postId, userId)
-> POST /api/posts/like
-> postController.likePost()
-> likes array toggled
-> server returns liked + count
-> frontend updates UI state locally

15. Strengths of the Current Project

  • Clear separation between frontend and backend.
  • Nice portfolio-friendly feature mix: auth, OTP, uploads, moderation, profile, likes.
  • Cloudinary integration avoids local file-storage complexity.
  • MongoDB schemas are small and easy to understand.
  • UI is more polished than a default starter app.
  • Service wrappers on the frontend keep code readable.

16. Weaknesses and Risks in the Current Implementation

This section matters if you want to explain the project professionally in an interview or present it as a serious production candidate.
  • Authorization is not enforced on sensitive post routes.
  • Anyone can choose the admin role from the register form.
  • Login stores JWT in both an HTTP-only cookie and local storage.
  • Some logout flows only clear local storage and do not always call the backend logout endpoint.
  • Post creation depends on user info sent from the client instead of deriving it from authenticated server state.
  • There is no validation library for request bodies.
  • There are no automated tests yet.
  • Some route actions like approve, reject, and delete should be protected with auth middleware.

17. Best Improvements to Make Next

  1. Protect post routes with protect and adminOnly middleware.
  2. Remove role selection from public registration and assign admin roles manually.
  3. Use server-authenticated user identity instead of trusting userId, username, and avatar from the client.
  4. Add validation for auth and post payloads.
  5. Use secure cookie settings for production.
  6. Choose one auth persistence strategy instead of both cookie and local token storage.
  7. Add tests for auth, OTP flow, and moderation logic.
  8. Introduce route guards on the frontend for admin-only and logged-in pages.

18. How to Explain This Project in an Interview

A good short explanation would be:

“Feedsss is a full-stack moderated social feed app that I built with React, Vite, Express, and MongoDB. Users can register, verify their email with OTP, log in, upload image posts through Cloudinary, like approved posts, and manage their own profile. Admin users can moderate pending posts before they go live. The frontend uses a service layer around Axios, and the backend is organized into routes, controllers, models, and middleware.”

19. Final Summary

Feedsss is a clean educational full-stack project with real product ideas: account verification, password recovery, image uploads, moderation, likes, and profile pages. Architecturally it is easy to follow, which makes it great for learning and presenting. Its biggest gap is backend security enforcement, not overall structure. If you tighten authorization and request validation, it becomes a much stronger project technically.
